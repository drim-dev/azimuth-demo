**The two findings columns are different currencies and should not be added.** Findings against the
app are defects in the product. Findings against the evidence are defects in the *account of* the
product — they are what the agent tier produces, and their value depends entirely on whether an
account that reads true matters when the product is already correct. That question is the ceremony
falsifier, and it is still open.

## What was actually demonstrated

**The site-class result, and it is the only strong one.** The residual in
`azimuth/model/trips/rider-view/verification.md` predicted, before any application code existed,
that a new rider-reachable surface would satisfy every behavioural claim and leak anyway. Slice 2
built the receipt; the matrix reported 23 errors before and 23 after. The invariant designed against that
evidence found all seven sites in the class and named the three that leaked.

That is a pre-registered prediction, confirmed, catching a real privacy defect that would have
shipped. It is also the clearest statement of what per-scenario tracing structurally cannot do: a
claim quantified over a *set of sites* is not established by evidence about one site, however good
that evidence is.

**Five decisions were revised by evidence rather than argument** — D12, D13, D14→D18, D15, and D7's
identity. That is the method working: notation last, evidence first.

**The agent tier found four defects on a matrix the machine tier called green**, and one of them
survived its own fix. Encouraging, and see the validity note below.

**The find → fix → verify loop closed, once, under mutation** *(added 2026-08-07)*. The
`trips/request` pass named three mutations it predicted the evidence would survive. The evidence was
rewritten and each mutation applied: a constant fare in place of the quote's total, a five-minute
grace window on expiry, and `'completed'` dropped from the `ux_trip_rider_active` filter. The old
tests passed all three; the new tests failed all three.

**What that is and is not.** It is evidence that a judgment's finding was specific enough to act on
and that the action was verifiable — the weakest link in a self-declared system is that "improved"
is unfalsifiable, and here it was not. It is *not* a defect found: every mutation was injected by
the same author, the implementation was correct before and after, and the currency of the ceremony
falsifier is defects the framework caught in the product. Two of the three mutations correspond to
drift `azimuth/model/trips/request/design.md` predicted in writing, which is the closest this gets
to a real failure mode, and it is still not one.

## What is compromised about all of it

One agent designed the framework, wrote the fixture, wrote the tests, tagged the code, and judged
its own tags. Every source of validity is weak except the pre-registered prediction — and the same
author wrote both the prediction and the leak that confirmed it.

The agent-tier result reads well and is the same author finding flaws in their own work an hour
later. That is *some* evidence the pass has value. It is not evidence that it works reliably, which
is what the falsifier asked for.

**Nothing further from this repo can settle it.** The demo can show a mechanism exists and can
demonstrate a class of defect it catches. It cannot show that the holes are real defects rather
than an artifact of having designed the fixture to have them.

## Update after mechanism-linkage design *(2026-08-10)*

D27 makes current mechanisms independently addressable. Every design entry now declares a stable
mechanism id. .NET and TypeScript can emit extractor-derived implementation bindings and separate
mechanism evidence; the core rejects missing, ambiguous and dangling relations and exports both.
Explicit bindings remain for the currently accepted product designs, so this migration changes no
claim about what the fixture implements.

Synthetic tests establish the key deletion property: removing the implementation edge while
leaving the design declaration produces `unresolved-design-binding`. This is tooling validation,
not product validation. No existing product mechanism has yet adopted `ImplementsMechanism` or
`CoversMechanism`, and no cross-spec application relation has been demonstrated. The next change
must select an existing shared mechanism if one is suitable, or build one only if none exists, and
measure whether the new distinction avoids duplicated claim evidence without hiding application
gaps.

Repository inspection found a suitable existing mechanism, so the next change should not invent
one: `Pricing.QuoteTokenCodec` signs and validates the same quote contract in Pricing, Trips and
Payments. It already has a universal tamper-rejection test, while its application spans service
registration and two consuming business paths. That makes it a sharper experiment than a local
state machine: it can validate `ImplementsMechanism` and `CoversMechanism`, and it forces the still
open question of how one concern-oriented design proves cross-spec application. The likely atomic
split is quote-token issuance (`Encode`) and quote-token validation (`Decode`); the change should
decide their design home and application domain from evidence rather than pre-installing a general
catalog.
