# Federation trial protocol

## Pre-registered hypotheses

| Id | Proposition | Falsifier |
|---|---|---|
| F1 | Splitting repositories preserves the assurance model. | A claim, relation, hole or judgment changes only because of repository placement. |
| F2 | Routine work remains local. | A one-repository routine requirement needs a catalog/model-repository edit or linkage artifact. |
| F3 | Complete assembly fails closed. | Any missing required input produces a complete green result. |
| F4 | Evidence is revision-bound. | A receipt for one revision tuple covers another tuple. |
| F5 | Area identity survives relocation. | Moving an unchanged area requires retagging or expires a judgment. |
| F6 | Semantic area changes are explicit. | An area split or merge is accepted as a locator-only move. |
| F7 | Change authority does not duplicate. | A cross-repository change needs independently authored proposals that can drift. |
| F8 | The agent tier is discoverable. | Cold agents routinely place intent or evidence under the checkout they start in rather than its authority. |

F7 is now machine-enforced: repository observations enumerate the actual tracked change tree and
complete assembly rejects an id with more than one authority.

## Workloads

### Local routine

`experience/display-density` changes only browser presentation and browser-local persistence. The
accepted path is one intent package and ordinary implementation. No complete workset is needed
during authoring; complete integration is required only before the project snapshot that accepts a
multi-repository release candidate.

### Cross-repository routine

The conformance fixture's capture identifier is passed from Payments to the rider receipt. In a
field replication, keep it routine and require backend plus experience work packages without adding
critical evidence solely because two repositories participate.

### Routine collateral review

Edit presentation inside a typed source that also realizes a critical claim. The routine claim must
remain intent-only; the critical judgment over the changed source must expire. Repeat the same edit
outside a critical source and require zero judgment churn.

### Critical cross-repository

The executable fixture models a critical receipt projection across backend, experience and E2E
areas. The field workload is referral-credit expiration: authoritative time and reservation in the
backend, selector exclusion in experience, detector rules in operations and a composed receipt in
assurance. An execution receipt must name all selected revisions.

## Git and integration sequence

One semantic change id may name one branch per participating repository. Backend compatibility is
merged first; experience and operations follow independently. Integration CI selects commits rather
than branch names, runs composed evidence, emits a receipt over the exact tuple and only then writes
a project snapshot. Git cannot atomically merge several repositories, so Azimuth must represent
intermediate compatible states rather than inventing an atomic transition.

## Topology evolution

1. Move a file inside one mount: only its locator changes.
2. Rename a repository: project mapping changes; source identity does not.
3. Move a whole area to a new repository: area/address identity and judgment stay current.
4. Split an area: assign new area identities through an explicit semantic change.
5. Render a pre-split archived snapshot: old repository revisions and manifest digests remain
   visible even when the current topology differs.

## Hard acceptance conditions

- zero false green results in the fault matrix;
- zero tag changes for a whole-area relocation;
- zero reuse of a receipt against a different revision tuple;
- zero duplicate authority for a spec or area;
- no project finalization from a local or dirty assembly;
- no linkage obligations for the local routine workload.
- no accepted project snapshot unless one unchanged change directory moves from its singular active
  authority to the dated archive between two complete, receipt-bound worksets.
